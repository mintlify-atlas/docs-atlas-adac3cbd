The Fact is present-state only. A `DESIGN.md` describes what a component *is*, never what it *used to be*. But history has to live somewhere, or it is simply lost. It lives beside the Fact, in two logs — and those two logs are not interchangeable. They have different lifetimes, different rules, and a strict dependency direction that keeps permanent records from rotting when transient ones disappear.

## Fact ≠ Narrative

This is ideology 2 of the DTDD methodology: **present-state docs are the Fact; the logs are the narrative of change.** Splitting them is what stops the Fact from rotting into a changelog. A `DESIGN.md` that accumulates "replaced X with Y on \<date\>" sentences is no longer present-state — it is a diary wearing a design doc's name.

Every fact about *why* something changed, or *what was tried and rejected*, goes into a log instead. Two logs, because history splits cleanly into two kinds with different lifetimes: decisions that are permanent and improvements that are transient.

**Canonical locations.** Each log lives in its own folder under `docs/`:

- `docs/decisions/decisions-log.md`
- `docs/improvements/improvements-log.md`

This is what `/dtdd-init` scaffolds, and the paths the commit gate's dangling-reference check watches. A folder per log is deliberate — each can accrue siblings with the same lifetime (superseded decision attachments beside the permanent log; per-area improvement notes beside the transient one) without mixing the two lifetimes in one directory.

## The Decisions Log

The decisions log is a **permanent, append-only record** of confirmed decisions — architectural, product, or process. It is the only home for history in a DTDD repository.

A confirmed decision is recorded here on its own terms: what was decided, what alternatives were considered and rejected, and why. Once written, an entry is **never edited** to track the current code. If a decision is later reversed, a *new* entry records the reversal; the old entry stays, because it is true that the decision was made and true that it was later changed. The log is a timeline, not a mirror of today's state.

### Entry Format

<CodeGroup>
```text Generic form
**Retry policy: exponential backoff, capped at 5 attempts**
Considered a fixed retry count with linear delay. Rejected because a downstream
outage produces a retry storm at a fixed interval. Landed on exponential backoff
(base 200ms, cap 5 attempts) so retries space themselves out automatically.
```
</CodeGroup>

Notice what is absent: no ticket ID, no run ID, no "as of Q3." The entry is self-contained and ordered by its position in the log. One exception: an entry that **supersedes an earlier one** carries a date prefix in its title — `**YYYY-MM-DD — <title>**` — so the reversal's ordering survives even a later reorganization of the file.

### Structure Rules

- **Grouping.** Entries are grouped under a level-2 heading naming the area (e.g. `## Payments Service`, `## Data Model`). A new area gets a new heading; later decisions are appended under the existing heading in the order they were made.
- **No numeric IDs.** Entries are identified by their bold title line, not by a monotonic ID like the improvements log's `IMP-XXX`. Nothing elsewhere in the repository needs to reference "decision #14" — a `DESIGN.md` describes the current design directly, and this log is read start-to-finish or grepped by title, never looked up by number.
- **No `IMP-XXX` citations.** The decisions log never cites an improvements-log entry. A decision's substance does not depend on a tracker entry that might not exist tomorrow. If context from a transient log matters to a decision, that context is restated in the decision's own words — never referenced by ID.

## The Improvements Log

The improvements log tracks **improvements to the existing implementation** — drift, missing edge cases, duplication, tooling gaps. It is explicitly not a feature backlog and not a design doc. A new capability belongs in a plan or in a `DESIGN.md`'s open questions, not here.

Unlike the decisions log, this log is **transient**: entries are deleted on resolution, not marked "resolved."

### IDs and the Next-ID Counter

IDs are monotonic and never reused. Each entry gets `IMP-<n>` from a **Next-ID counter** kept in the log's header — not by scanning the file for the highest number currently present, because entries are deleted once resolved, so the highest surviving number understates history. The counter, incremented every time an ID is issued, is the only source of truth for what is next.

### Status Lifecycle

Entries move through three states: `open` → `in-progress` → **deleted**. There is no `resolved` status. An entry that is done does not get marked done — it leaves the file. The log only ever shows what is still outstanding.

### The Three Lifecycle Rules

<Steps>
  <Step title="Scan before work">
    Before touching an area, check the log for an entry whose scope overlaps the files about to change. If one exists, mark it `in-progress` rather than duplicating the same finding under a new ID.
  </Step>
  <Step title="Cite in commit">
    When work resolves an entry, the commit message references its `IMP-<n>` so the link from code history to the tracker is searchable later — even though the entry itself is about to disappear from the log.
  </Step>
  <Step title="Sweep references on delete">
    Deleting an entry is not just removing its block from the log. Grep the repo for that ID across docs, comments, and other logs, and fix every dangling reference in the *same* change. A citation to a deleted entry is worse than no citation — it points a future reader at nothing.
  </Step>
</Steps>

### Entry Format

<CodeGroup>
```text Generic form
### IMP-012: retry logic duplicated across the payments client and the
email-sender client
- **Severity:** medium
- **Status:** open
- **Area:** `payments/client`, `email-sender/client`
- Both clients hand-roll the same exponential-backoff loop. Extract one shared
  retry helper; both callers adopt it.
```
</CodeGroup>

Severity levels are `critical` (actively breaking or blocking), `high` (meaningful risk — drift, silent failure, missing hot-path coverage), `medium` (quality or maintenance concern), and `low` (nice to have).

## The Lifecycle-Aware Dependency Direction Rule

This is ideology 3, and it is the load-bearing rule that makes the Fact/Narrative split safe: **a permanent artifact never points at a transient one.**

<Accordion title="decisions-log.md never cites IMP-XXX">
  A decision's substance and rationale stand whether or not an improvement-log entry ever tracked the same area. The decisions log must remain fully readable after every entry in the improvements log is eventually deleted. Citing a transient ID in a permanent record means the permanent record silently loses meaning when that ID disappears.
</Accordion>

<Accordion title="DESIGN.md may cite IMP-XXX — but only as decoration">
  A `DESIGN.md` sentence *may* include an `IMP-<n>` citation as an optional pointer to more detail, but the sentence must still read correctly and completely if that entry is deleted the next day. State the current limitation in the present tense first — self-contained — and treat the `IMP-<n>` citation as decoration on a fact that already stands without it. Never use it as the explanation itself.
</Accordion>

<Accordion title="No run IDs, seam IDs, or ticket IDs in any permanent doc">
  No document or piece of code cites a run ID, a seam ID, or a ticket ID from the process that produced it. Those identifiers belong to a task-tracking system outside the repo. A task tracker is even more transient than the improvements log — it can be migrated, renamed, or shut down entirely without the repo knowing. A repo fact that depends on an external tracker's ID for its meaning is a fact that can silently go stale.
</Accordion>

The direction only ever runs one way: transient artifacts may reference permanent ones (an `IMP-<n>` entry can say "see the decisions-log entry on retry policy"), but never the reverse. A permanent record that depended on a transient one would inherit that transient one's mortality.

<Warning>
  The DTDD commit gate checks for dangling `IMP-XXX` references automatically as part of its pre-commit hook. If you delete an improvements-log entry without sweeping the repo for references to its ID, the gate will block the commit. Fix every reference in the same change that removes the entry — not in a follow-up.
</Warning>
